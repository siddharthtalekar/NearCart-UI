# MASTER PROMPT: Build the complete NearCart frontend UI

## ROLE
You are a senior frontend engineer and UI/UX designer. Build the COMPLETE frontend
of "NearCart" using React (Vite), HTML, CSS and JavaScript. Frontend only: no real
backend. Use mock data and a mock service layer so every screen is fully clickable
and realistic.

## PRODUCT SUMMARY
NearCart is a hyperlocal marketplace. Shoppers discover nearby independent stores,
compare products and prices across stores, and order with local delivery. Shop
owners manage listings, stock and offers. Delivery partners fulfil orders. Admins
approve and monitor everything.

## TECH CONSTRAINTS
- React 18 + Vite, JavaScript (no TypeScript), React Router v6
- State: React Context + useReducer (auth, cart, orders, notifications)
- Styling: plain CSS with CSS variables (design tokens) + CSS Modules or one
  global stylesheet per feature. No UI kit like MUI or Bootstrap.
- Icons: lucide-react. Charts (admin/owner dashboards): recharts.
- No localStorage dependency for core logic; keep state in memory (optional
  persistence behind a small storage helper with try/catch).
- Mock data in /src/data/*.js, accessed ONLY through /src/services/*.js
  (async functions with small delays) so the real Firebase/Java API can replace
  them later without touching components.
- Map placeholders: a styled map component (static image/SVG with pins) behind a
  <MapView/> wrapper, so a real mapping service can be dropped in later.
- Payment placeholders: a <PaymentGatewayMock/> modal; real gateway is TBD.

## BUSINESS RULES THE UI MUST ENFORCE
- Everything customer-facing is limited to the confirmed delivery area.
- Product comparison never equates different size/brand/variant.
- Checkout re-validates stock, price, offers and total; changes are shown clearly
  before the order is placed.
- Duplicate-order prevention (disable button, idempotency key in mock service).
- All fees are visible before payment.
- Orders reach final statuses: Delivered, Rejected, Cancelled, Failed.
- Owners and partners cannot operate until admin approval.
- A notification is generated at every order stage.

## DESIGN SYSTEM
- Modern, trustworthy, local-marketplace feel: warm primary (e.g. emerald/teal),
  accent orange for offers, neutral greys. Define all colours, spacing, radius,
  shadows and typography as CSS variables. Support light AND dark mode via
  prefers-color-scheme plus a manual toggle.
- Font: Inter (with system fallback). 8px spacing grid. Rounded cards, soft shadows.
- Fully responsive:  desktop first . sidebar layouts for owner/admin/delivery on desktop.
- Accessibility: semantic HTML, labels, focus states, keyboard navigation, ARIA
  for modals/tabs, colour contrast AA, prefers-reduced-motion respected.
- Every list/page needs loading (skeleton), empty and error states.
- Toasts for all actions; confirmation modals for destructive actions.
- Subtle transitions only; no heavy animation.

## MOCK DATA REQUIREMENTS
- 12+ stores across categories (grocery, pharmacy, bakery, electronics,
  stationery, etc.), 60+ products with size/brand/variant fields, some identical
  products across multiple stores with different prices/stock.
- Sample users for each role, 20+ orders in varied statuses, offers, disputes,
  notifications, and fraud flags. Use Indian context (INR, Pune area names).
